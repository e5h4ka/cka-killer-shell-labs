## После утверждения: локальная проверка

1. Проверка schema/catalog: ровно 20 и 17 ID, обязательные файлы и capabilities, отсутствие ссылок на несуществующие assets, LF и executable bit.
2. bash -n и ShellCheck для собственных shell scripts; Python compile и unit-tests для state, identity, partial failure, ownership и семантических checks.
3. Положительные и отрицательные fixtures: чужие Pod owners, Running без Ready, Pending из-за ресурсов, broad RBAC, отсутствующий API, изменённый namespace UID, прерванный setup, повторный cleanup, недоступный recovery API.
4. Kustomize render обоих overlays, YAML/JSON validation. Client dry-run не считать подтверждением server admission/CRD совместимости.
5. Валидаторы файлов не исполняют произвольные ответы как root. Для скриптов kubectl: статическая проверка и исполнение с read-only kubeconfig, таймаутом и ограниченными правами ОС. Скрипт renew из 1/14 только читать.
6. Зависимости: сверка pinned URL/version/digest/checksum, доступность образов и наличие требуемых утилит. Недоступность фиксируется отдельно от FAIL решения.

## Настоящий Kubernetes: критерии каждой задачи

Свежая поддерживаемая сессия → doctor → start → validate исходного нерешённого состояния (FAIL по целевым требованиям) → решение → validate (PASS всех обязательных пунктов) → намеренное неверное изменение (FAIL нужного пункта) → восстановление → cleanup → health-check → повторный start.

Для системных задач дополнительно прервать выполнение после fault injection, проверить recovery при отсутствии API, повторный recovery и остаточные изменения. Для ServiceCIDR проверять предусмотренный переход к новой сессии, а не обещанный rollback. Для NetworkPolicy проверять реальные allow/deny с доступными targets; для Gateway — реальные HTTP ответы; для volumes — запись и чтение; для readiness/scheduler/Service deletion/runtime events — checkpoints до потери промежуточного состояния.

Перед выдачей статуса «проверено в Killercoda» сохранить: git SHA, task ID, дату, фактические Kubernetes/runtime/CNI/proxy/Helm версии, topology, команды, вывод проверок, длительность, cleanup/recovery результат. Не включать токены, приватные ключи, реальные Secrets или etcd snapshot в git. Пропущенный, несовместимый или непроверенный сценарий не считается пройденным.

## Передача пользователю после реализации

В итоговом сообщении будут точные существующие команды git clone --branch dev, перехода в каталог и start/validate/hint/cleanup для каждого набора; SHA отправленного коммита; таблица готовности 37 задач; локальные результаты отдельно от кластерных. Сейчас этих исполняемых команд ещё нет.

Отчёт пользователя: ID задачи; SHA; playground/topology; шаги; ожидаемый и фактический результат; вывод doctor/validate; удалось ли cleanup/recover. После отчёта исправления выполняются в dev, коммиты по существенным исправлениям, один push после проверки этапа. main и merge остаются под отдельным разрешением пользователя.
